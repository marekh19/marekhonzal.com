Your laptop is a terrible place for an AI agent to live.

A couple of guys at the office told me how they keep their agents running on the way home.
They have something set up to keep their MacBooks awake with the lid closed. Before
leaving, they connect to a hotspot, put the laptop in a backpack, and hope the connection
holds for the journey.

I get it. I've repeatedly wanted to leave while an agent was still working. But keeping a
computer awake in a backpack is a lot of effort just to let a task continue.

For the past month or two, I've run Claude Code and Codex almost exclusively on my home
server. I connect over SSH through Tailscale. When I close the laptop, the work continues.
And when I have an idea before bed, I can give the agent a task from my phone and come
back to it the next morning.

I'm a terminal guy. I was already comfortable working in Neovim before coding agent
harnesses were a thing. I prefer terminal interfaces, and I think coding agents are
particularly well suited to them: the agent, shell, tests, and Git are all right there. If
you want a graphical editor and agent interface, this setup isn't for you. If you're
comfortable in a terminal, I'd say move your agents off your laptop; you won't regret it.

## Leave when you want to leave

Remote development has existed for years. I didn't bother with it before because I was the
one writing the code, researching questions, and collecting resources. When I left the
keyboard, most of that work stopped anyway. Moving it to another machine didn't offer me
enough benefit.

Agents changed that. I can assign work that continues between my check-ins, so it makes
sense for the environment to stay available independently of the computer I'm carrying.

Longer research fits this well too. Comparing features, reading standards, collecting
resources, or investigating possible improvements can take a while. I can leave that
running and come back to the findings. If the agent needs an answer, I can reconnect from
my phone, answer, and let it continue. Sometimes the result needs more work or a decision
from me. That's fine; I pick it up when I'm ready.

**The benefit is convenience.** I don't want to think about whether my laptop's battery,
Wi-Fi connection, or lid will interrupt the work. An agent that finishes and sits idle
until I return is doing exactly what I need. I have no interest in stressing about not
utilizing it literally 24/7 or not using my subscription's full token allowance in every
five-hour window.

## What runs where

My setup has three main pieces:

- **Ubuntu Server:** The server runs Ubuntu and hosts my repositories, development tools,
  and agent clients. Builds and tests run there too. I know Ubuntu well. It's been stable
  for me, and documentation is easy to find. I've used this machine for almost four years,
  replacing every component but the SSD without trouble.
- **[Tailscale](https://tailscale.com/) and SSH** let me connect to that machine from my
  laptop or phone (I like to use [Termius](https://termius.com) on my phone). I use
  ordinary SSH over Tailscale's private network.
- **[herdr](https://herdr.dev/docs/)** keeps the terminal sessions running when I
  disconnect and lets me return to them later. I used tmux for several years; herdr adds a
  sidebar that shows whether each agent is idle, running, done, or blocked, for example
  waiting for an answer. I can see which session needs attention without opening each one.
  On mobile, the sidebar collapses into a hamburger menu.

The agent clients and their tools run on my server. The models run at the hosted AI
providers. You don't need to buy hardware for local model inference to do this. Your
machine needs to handle your development workload and however many tasks you run at once.

Tailscale lets me reach SSH and my dev servers remotely **without exposing them to the
public internet**. I don't have to open public ports for either. Its
[connection guide](https://tailscale.com/docs/how-to/connect-to-devices) explains how to
reach services using a device's Tailscale address.

The persistent sessions survive a disconnected client. After a server restart, herdr
restores its spaces, windows, and panes, and resumes agent sessions for clients whose
[integrations](https://herdr.dev/docs/integrations/) you have installed. The restart still
stops running processes: dev servers and other processes in those panes need to be started
again.

## The same development loop, from another machine

This is how I start:

```bash
ssh homelab
hd
```

`homelab` is a short name in my SSH config, and `hd` is my alias for `herdr`. Without my
aliases, you'd SSH to your server and run `herdr`.

Once inside, I can see the state of agents in different repositories and switch between
them. I can have several tasks running in parallel and give each one attention when it
needs it. Reconnecting from another device brings me back to those same sessions.

For a web project, I start the dev server in a terminal on the server, just as I would on
my MacBook:

```bash
pnpm dev --host
```

In my projects, `--host` makes the dev server listen on `0.0.0.0`, so I can reach it from
another device. Use the equivalent option for your project's dev server. Then I open this
address in my MacBook or phone browser:

```text
http://<server-tailscale-ip>:<dev-port>
```

Use the port printed by the dev server. A resolvable Tailscale device name works too; the
`homelab` shortcut in my SSH config doesn't automatically become a browser hostname. The
client needs to be connected to Tailscale and allowed to reach that port.

In my setup, I also route my home subnet through Tailscale, so I use the server's home LAN
IP instead. That gives me one URL at home with Tailscale off and away with Tailscale on.
You don't need subnet routing if you use the server's Tailscale address above.

The server is headless, with no browser. I test the feature in a real browser on the
device I'm holding: click through it, inspect the behavior, and ask for changes. Nothing
needs to be deployed just for me to try it. `0.0.0.0` listens on all IPv4 interfaces, so
it can also allow home LAN access; it doesn't itself restrict access to Tailscale.

From there, it's the usual development workflow. I inspect the changes, run tests, try the
feature, and ask the agent to commit, push, and open a PR when I'm satisfied. I can also
leave it working toward a draft PR and review that later.

The phone is useful for short prompts, checking progress, and answering questions. I can
review a manageable PR through GitHub's interface on the way home and merge it when I'm
happy with it. It's less comfortable than reviewing on a computer, but having the option
is useful. Longer reviews can wait until I'm back at my desk.

I ran into subnet-routing problems with this setup. Advertising a broader subnet fixed
them for me; Tailscale's
[subnet routing guide](https://tailscale.com/docs/reference/troubleshooting/network-configuration/lan-traffic-overlapping-subnets)
explains the approach and its limitations. I'll cover my networking setup and the other
services on my homelab in a separate article later this year.

## The server I actually use

I already had a home server, so adding development to it was an obvious choice. It runs
around 20 containers, including Home Assistant, Jellyfin, Frigate, Umami, and more.

The current machine has an **Intel Core i5-13500, 32 GB of RAM, one small NVMe SSD, and
two larger 3.5-inch data HDDs configured as a RAID 1 array**. I started with used parts
from Aukro.cz roughly four years ago and upgraded it over time:

| Purchase                     | What I bought or changed                          | Approximate cost |
| ---------------------------- | ------------------------------------------------- | ---------------: |
| Original machine             | Used parts, including an i5-9400 and 12 GB of RAM |        8,000 CZK |
| RAM upgrade                  | Increased RAM to 32 GB, bought used               |        3,500 CZK |
| CPU upgrade                  | Used i5-13500, replacing the i5-9400              |        4,000 CZK |
| Motherboard upgrade          | Replacement required for the newer CPU's socket   |        2,000 CZK |
| **Total of these purchases** |                                                   |   **17,500 CZK** |

The old CPU was still usable. More parallel work, alongside the other services, motivated
the upgrade. My smart socket reports roughly **40 W at the wall** during typical use, with
the containers, some agent instances, a dev server, and the two data HDDs. That's an
observation from my normal workload, not an idle-power measurement.

I'd buy an upgradeable tower for this. I prefer a standard ATX platform, with room for
more RAM, storage, and ordinary replacement parts. I'm happy to give it more space instead
of paying the premiums I associate with ITX boards and SFX power supplies. The development
workload determines what you need: builds, tests, and containers still consume resources
even when the model runs elsewhere.

## Make it feel familiar

I use Fish, Neovim, ripgrep, fzf, Delta, lazygit, and the same CLI tools I used before
agents. My [dotfiles](https://github.com/marekh19/dotfiles) keep the configuration
familiar, with GNU Stow managing it. Connecting to the server puts me in an environment I
already know how to work in.

## Try it on a machine you already have

Start with one repository on a spare machine that can stay running, or an existing home
server:

1. Install [Ubuntu Server](https://ubuntu.com/server/docs/tutorial/) if needed, then your
   usual development tools and coding agent.
2. [Set up Tailscale](https://tailscale.com/docs/how-to/quickstart) on the server and your
   client devices, and configure SSH access over that network.
3. [Install herdr](https://github.com/herdrdev/herdr#install), clone your project's
   repository, and run `herdr` on the server.
4. Start your agent inside it and give it a task.
5. Disconnect, reconnect from another device, and run `herdr` again to return to the
   session. For a web project, try opening its dev server in that device's browser too.

You can give this article to an agent and ask it to help you set up those pieces.
